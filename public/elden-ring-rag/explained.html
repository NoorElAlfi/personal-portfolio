errag, explained

A personal Elden Ring lookup. Two tiers, deliberately kept separate, backed by a local SQLite file — no vector store, no search index, no model required.

Every number and claim below comes from the project's README. Nothing here was measured fresh for this page, and the page makes no network requests.

Two tiers, kept apart on purpose

The whole design is a bet that "where do I find X" and "what do I do next" are different problems, and answering both with one retrieval mechanism would serve neither well. So there are two question shapes and two answers.

Tier 1 · item

where

"where can I find X" — one question, one row. A SQLite row lookup with fuzzy entity resolution, returning a cited source URL.

It is a lookup, not a synthesis: the job is to find the right line in the corpus and refuse to guess when it can't.

Tier 2 · quest

quest

"what should I do next", "did I miss a quest" — ordered steps, filtered by region or section.

Its entire value is the ordering, so it is served as a sequence, not as chunks to be ranked.

Why separate rather than one unified retriever: a lookup wants exactly one item and a loud failure when nothing fits; an ordered walkthrough wants the document whole and in order. Chunking the quest document to feed an embedding index would destroy the ordering that is its entire value, and a top-k search over item names would return five near-identical neighbours when what you asked for is one of them.

The pipeline

From wiki pages to a cited answer. Fetch is the only stage that ever touches the network, and only when you explicitly ask it to; every later stage runs offline against the local database.

The dashed callout marks the one stage with any uncertainty: fetch refuses to run without --yes, because fandom.com's robots.txt is served behind Cloudflare and its automated-access policy could not be read.

What each stage does

  • fetch — optional and explicit. Pulls Fandom item pages and caches them as local JSON (data/raw/items/*.json), skipping pages already present unless asked to refresh. One-off, low-volume personal use is the intended line; bulk harvest or redistribution is not.
  • ingest — parses the cached wikitext into rows: each item (display name, location, effect, source URL, and a curated flag), one or more alias keys per item for fuzzy resolution, the full page prose chunked by section into passage, and the quest document into ordered quest_step rows.
  • normalise + synonyms — names are lowercased, apostrophes unified, possessives stripped, then expanded through PHRASE_SYNONYMS. This is how community shorthand that appears in no in-game name still resolves: "ball bearing" → "bell bearing", "somber smithing stone" → "somberstone".
  • tier 1 / tier 2 — either a scored lookup across the alias table, or a filtered, ordered read of the quest steps.
  • answer — always carries its source URL, so the provenance is visible and stayable.
  • chat — optional and strictly downstream. Retrieval runs first; a model then answers only from what was retrieved and cites it. No model is required for any of the above.

Why no vector store and no FTS5

Both omissions were measured, not assumed. They are the two decisions the project is most likely to be asked about, so they are worth stating plainly.

No FTS5

The FTS5 trigram tokenizer was tried first: it returns zero rows for match 'smberston' and cannot rank. Since the corpus is at most a few thousand rows, a token-set scorer in Python is simpler and strictly better. The stated revisit point is a corpus past roughly 100k rows — well beyond what this ever holds.

No vector store, no embeddings

  • Tier 1 is a lookup, not a synthesis. Top-k cosine retrieval would blur the five near-identical Bell Bearing [n] entries together, when the whole question is which index.
  • Tier 2 is 2.7k words total, which fits in a context window whole. Chunking and embedding it would destroy the ordering that is its entire value.

Synonym expansion stands in where a learned alias model might otherwise go: the mappings are hand-curated and only cover shorthand that appears in no in-game name, which is why a conflated query like "somber smithing stone ball bearing 1" can still land on the right item and report the genuinely ambiguous alternative.

One where query, end to end

Follow "somber smithing stone ball bearing 1" — a player's shorthand, containing no exact item name — from raw string to a cited answer.

1. ExpandSynonyms rewrite the shorthand: ball bearing → bell bearing, somber smithing stone → somberstone.
2. ScoreA token-set scorer compares every expanded variant against every alias and ranks the best match per item.
3. GuardA trailing index is checked against the item's display name, so [1] can never be answered with [2].
4. GateThe top score must clear ANSWER_MIN = 0.72, or the tool declines rather than guess.
5. AnswerConfident: one card with its source URL. Otherwise: ranked suggestions, or an explicit "nothing matched".

Two things make this more than a fuzzy string match. First, the index guard: every indexed item also carries an index-stripped alias, so without checking the display name the tie between [1] and [2] would be unbreakable. Second, the confidence gate: a score below 0.72 does not produce a wrong answer, it produces a ranked list and a non-zero exit. This is exactly the mechanism the golden set caught when a query tied between the correct item and Smithing Stone [1], and it is why the tool is built to fail loudly rather than confabulate.

The exit-code contract is part of the interface, not an afterthought:

ExitMeaning
0Answered — a confident match was found (or --all listed every match).
1No confident match — scores below the threshold; ranked suggestions are printed instead.
2Nothing in the corpus matched at all.

Two further honesty behaviours are enforced the same way: an item whose source page carries no ==Acquisition== text says (no acquisition text in corpus) rather than inventing a location, and every resolved item shows its source URL.

What counts as correct: eval and overrides.json

The project's real specification is not this page or even the README — it is data/eval/golden.json plus a set of invariants, run by errag eval, which exits non-zero if any case fails so it works as a pre-commit or CI gate.

Two kinds of check, deliberately kept distinct:

  • Answer cases — a query, the item it must resolve to, and optionally a substring its location must contain. These are written from knowledge of the game, not generated from the database: a case read out of the database passes no matter how wrong the database is, which is the failure mode worth avoiding.
  • Invariants — properties that must hold for every row regardless of content, so they cannot be satisfied by a lucky lookup: every located item carries a source URL; no duplicate display names; no unescaped entity artifacts; no navigation pages ingested; every item has a resolvable alias.

The golden set is the project's memory of its own bugs: it is what caught the scoring tie above, and the three regressions that widening the corpus introduced. The rule is to add a case every time a wrong answer slips through.

The curated escape hatch

Scraping cannot supply facts that require a judgement call, nor fix facts the source got wrong. data/curated/overrides.json is merged on top of the scraped corpus after every build, keyed by item name (any casing or punctuation — keys are normalised). A key matching an existing item overrides its fields and marks the row [curated] in output; a key matching nothing and supplying a location is added as a brand-new item. That covers both stub pages with an empty ==Acquisition== and anything no wiki page carries at all.

Known limitations

Stated plainly, because the tool is built to be honest in its output and this page should be too.

  • The quest document's DLC section is truncated. The source ends mid-sentence, yielding 13 DLC steps with no region tags, versus 272 base-game steps of which 170 are region-tagged. Base game coverage is good; DLC is not.
  • 287 of 2,725 items have no location — their pages exist with an empty ==Acquisition==. They still answer, with the explicit "no acquisition text" line.
  • category is empty for most armaments. It is read from the page's own [[Category:...]] links, and Fandom's weapon pages carry none — verified: Moonveil's wikitext contains zero occurrences of Category:.
  • Region derivation is best-effort. 1,448 of the 2,438 located items resolve to a region from the location prose; the rest never name one.
  • Versioning is curated-only, because it was measured. Every cached item page was checked for a version marker; none carries one. The only version signal anywhere is {{SOTE}} on a category index page, which flags exactly 10 bearings as Shadow of the Erdtree. game_version is never guessed.
  • Chat retrieval is heuristic and thinly tested. Entity detection prefers boss pages on combat words, and treats a curated generic word list (weapon, armor, ash, ...) as never an entity. Both are judgement calls, and only six retrieval cases are covered by errag eval.
  • Retrieval depends on pages being fetched. Affinity, Scaling and Stats are redirects, and Ashes of War uses an empty infobox, so all were silently absent until redirect resolution was added. If a chat answer looks empty, the fix is to run errag chat --backend none and read what was actually retrieved before blaming the model.
  • No model is bundled. chat is useful without one (context-only), but natural-language answers need ollama installed or OPENAI_API_KEY set. The request/response plumbing is verified against a stub server; the quality of any particular model's answers is not.

The through-line: every stage is built to say what it does not know — a below-threshold query declines, an unlocated item says so, an unversioned item claims no version, and --backend none shows exactly what retrieval returned before any model touches it.
