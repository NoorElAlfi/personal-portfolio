SIEM Guard, explained

How a security-log pipeline turns raw text into alerts: where an LLM is used, where it isn't, and how an isolation forest decides what's unusual.

Every number below (features, medians, z-scores) came from running the real code on a small generated ssh population. Illustrative, not captured from a run: the LLM's reply in step 7, the sshd[9812] process id, and the 2D scatter in the forest demo.

The big picture

Two hard problems, two different tools. Understanding messy text is an LLM job. Deciding what is unusual is a statistics job: the LLM never makes that call, it only writes the explanation afterwards.

Models: qwen2.5:7b parses (at the top), mistral:7b explains (at the bottom). Both run locally through Ollama.

How an isolation forest works


Anomalies are easy to isolate. Pick a random feature and a random cut, and repeat until a point is alone. Points in the crowd need many cuts; an outlier is alone after a few. Average that over 200 random trees and you have a score. Click "Isolate fully" a few times on the outlier, then on a normal point, then "Run 200 trees". How it is used here


    

  • Each entity (an IP address) has its events cut into windows of 5, and each window is summarised as 8 numbers: failed-login ratio, logins per hour, distinct users, distinct ports, connection duration, bytes, geographic changes, and off-hours share.
    • 

  • One forest is trained across all entities. It asks: does this entity look unlike everyone else?
    • 

  • Before trusting the forest, a robust median/MAD check runs on every feature. At least two features must deviate strongly (z above 3.5), otherwise the forest's opinion is ignored. This is the gate.
    • 

  • A score above 0.6 is flagged.
    • 



Why the gate exists: min-max scaling forces the most isolated entity in any population toward a score of 1.0, even if everyone is clean. Requiring two independent deviations stops one typo'd login from becoming an alert. Try all four entities below.

Known weaknesses


From Session 41's scale sweep (100 to 50,000 entities): recall stays 1.00 at every size, but two problems show up at every size, including the smallest.


    

  • The ssh gate leaks about 1.8% of clean entities: a typo'd login (zero spread on that feature, so z is infinite) plus ordinary jitter in logins per hour clears the two-feature gate.
    • 

  • Per-entity forests (built only for entities with 3 or more windows) have no gate, so in the self-scoring detect() path they flag every such entity.
    •
