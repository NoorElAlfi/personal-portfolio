SIEM Guard parses log traffic and scores it for anomalies. By my own count this stretch is over ten sessions or improvements, and most of the hard work was not new detection logic. It was finding the places where the pipeline was quietly not doing what I assumed: a tuning knob that changed nothing, a scoring floor that could not see part of its own input, a corroboration gate that withheld detections, and a batch parser that could hand back transposed field values with the position between request and response lost.

## The false positives were not a tuning problem

I started from the false-positive structure, on the assumption that the contamination parameter was steering results. It is inert: changing it does not change results. That is worth saying plainly, because the intuitive work on false positives — turn it up, turn it down — was never going to move anything. The parameter stayed in the code as something to tune until it was removed as dead in Session 37.

The real defect sat in the population-forest floor, which is blind to degenerate features. A full-pipeline test of the false-positive-reduction fixes root-caused a missed case to that blind spot. The fix landed in the floor itself, in Session 15C. Earlier in the series, the results dashboard was hardened to consume real pipeline data instead of standing in for it.

## Detections that were being withheld

SSH behavioral detection was losing events. Recovery came from two directions: entity-identity and population-scoring fixes in Session 23, and a LILAC corroboration gate that was withholding detections it should have let through, fixed in Session 21. The gate fix is the part I keep thinking about. Nothing errored and nothing looked malformed; the detection simply never appeared, which is the failure mode that costs the most trust.

## Parsing integrity, not coverage

Batch parsing had both integrity gaps closed: field values could come back transposed, and positional integrity between the request batch and the response was not preserved. A transposed value is more dangerous than a missing value, because it is well-formed and wrong. Version fields carrying a `v` prefix had no guidance, so those values parsed inconsistently. `test_basic.py`'s async tests were broken, which meant the suite was not exercising the code it claimed to; those were fixed too, and the sessions were renumbered ahead of the merge into main.

## The LILAC template cache

The template cache and its hierarchical sampling were built standalone before being wired into `LLMLogParser.parse_async`. Two extraction faults surfaced: extraction was dropping short or normalized fields, and `template_cache.py` had a substring-collision bug that was confirmed and documented rather than left implicit. I think the ordering helped. Both faults were in the cache's own behaviour, and both were easier to reason about while the cache was still on its own rather than buried under a parser.

## Models, observability, and what I am not writing about

The most recent sessions split the default models by role — `qwen2.5:7b` for parsing, `mistral:7b` for reasoning — driven from config rather than hard-coded, and added origin-tracked `failed_llm` rate observability alongside a two-corpus dashboard refresh. That is Sessions 36 through 38, and with the earlier ones it is a real, session-numbered trail in the repository.

I also wanted to write about the JEV/semif experiment, and I am not going to. There is no commit, PR, or release in this window that names it. I cannot tell you what it tested or what it found, and inventing a tidy version now is exactly the post this one is trying not to be. It goes in when there is something in the repository to point at, and not before.

Two habits earned their keep here: checking that a parameter actually changes results before tuning it, and running the whole pipeline on a real case instead of trusting a single stage. The inert contamination parameter is the argument for checking; the missed case that the full-pipeline test root-caused is the argument for running the whole thing.
