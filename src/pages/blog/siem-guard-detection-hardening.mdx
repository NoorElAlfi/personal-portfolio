## The parameter that did nothing

I went into SIEM Guard's false-positive structure in Session 14B expecting to find a tuning problem and found something less comfortable: the contamination term was inert. It was present in the pipeline and it changed nothing about the outcome. Any experiment run against it would have measured a parameter that was not connected to a decision, which is a worse failure than a bad threshold — a bad threshold at least tells you where you are wrong.

Session 15B was meant to be a full-pipeline test of the false-positive-reduction fixes. Instead it root-caused the miss that was still getting through. That is a different result than the confirmation I was after, and a more useful one. Session 15C then fixed a degenerate-feature blind spot in the population-forest floor: the region of the input where the features that carry rarity information do not carry any, so the floor has nothing to separate on. A blind spot is not a number you can nudge; it is a place the detector cannot see.

## A template cache, built in two steps

The LILAC template cache with hierarchical sampling was built standalone in Session 16A and wired into `LLMLogParser.parse_async` in Session 16B. The order matters to me: standalone, the sampling policy is the only thing under test, and wiring comes second. Once the cache was live, its own defects surfaced. Template extraction was dropping short and normalized fields — legitimate fields that simply stopped appearing downstream. The substring-collision fix in `template_cache.py`, where one template's text can match inside another's, was confirmed and documented in Session 28.

## SSH recall, recovered after the gate fix

Session 21 fixed the LILAC SSH corroboration gate. The gate fix was necessary and it was not the whole story. SSH behavioral recall was recovered in Session 23 through entity-identity and population-scoring fixes — the recovery lived in how the pipeline decides what counts as the same entity and how behavior is scored against the population, not in the gate itself. I would rather write that down honestly than present the visible fix as the cause.

## Batch parsing that looks fine

Sessions 29, 30 and 31 closed integrity gaps in batch parsing. Session 29 fixed a positional-integrity gap, where values land under the wrong field position. Session 30 fixed a content-integrity gap where field values came back transposed. Session 31 fixed a version-field v-prefix guidance gap in package parsing.

These matter more than parse errors. A parse error is loud; a transposed value is not. The record validates, every field is populated, and downstream detection cannot tell a parsing bug from a genuine signal. That is the failure mode worth fixing before adding more detection.
