The population median/MAD gate leaks on degenerate features. Session 41 measured the ssh two-feature gate leaking ~1.8% of clean entities (http ~0.1%) because `failed_login_ratio` is MAD == 0 across the population — 75% of clean ssh entities are exactly 0, and 25% carry one typo'd `Failed password`, so those entities get z = inf on that feature and ordinary `login_frequency` jitter past 3.5 is enough to clear the two-feature gate; all 1,732 clean windows through the gate at 50,000 entities are that pair plus 3 with `unique_ports`, while http's residual 0.09% is `login_frequency` + `bytes_transferred_mean`. The same weakness is stated in `docs/SIEM_Guard_explained.md` ("the ssh gate leaks about 1.8% of clean entities"), with the general form that a feature whose population MAD is 0 gives z = infinity on any deviation. The cost of a fixed leak rate is that false-positive _count_ grows linearly — ssh went from 2 to 868 alerts across the sweep, with precision near 0.5 at a 2% base rate.

The per-entity tier has no gate at all. `_normalize()` min-max scales each entity forest's own training windows onto [0,1] and `detect()` scores those same windows, so an entity's most-isolated window is guaranteed to score exactly 1.0 > 0.6 whenever its windows differ at all: every clean entity in the `history` shape was flagged at 100% at every size tested (98 / 980 / 9,800 / 49,000), all via source `entity`, while the population tier alone flagged 0.00% of the same ssh entities. That is 50,000 forests, 4 GB and 33 minutes of work producing precision 2%. Two caveats are recorded with it: the flaw is specific to the self-supervised `detect()` path (score the training windows), and `detect_async()` — which scores new logs against a fitted baseline — was not exercised. A later note in the same document supersedes both: the entity tier was dropped after measuring 0 recall over the population tier in 120 anomalous-entity trials rather than repaired, and the ssh corroboration leak was fixed via a corroboration-independence group.

The ssh field-guidance mismatch is a schema problem as much as a prompt one. `docs/SIEM_Guard_explained.md` records from Session 40 that the ssh field guidance mentions `dur=`, `bytes=` and `geo=`, which come from the project's original invented format; real sshd lines have none of them, so those fields can only come back empty, and `duration`/`bytes`/`geoip_country` are 3 of ssh's 8 schema fields while `_batch_json_schema` marks every schema key required — forcing the model to emit three values that do not exist. Session 40 observed the consequence directly: `geoip_country` filled with a key fingerprint on an `Accepted publickey` line produced `geographic_changes = 0.2` for 192.0.2.28 and the run's only false positive. The same reader-shape problem shows up in timing and status: `TIMESTAMP_FORMATS` parsed ssh 167/167 but http 0/147 and ftp 0/105 on what the LLM actually returns (correcting Session 39's ground-truth-literal figure of 147/147), and `failed_login_ratio` reading only `status`/`result` meant 22 of 23 ftp `FAIL` lines registered as not-failed after the model glued `OK`/`FAIL` into `action`.

The parsing-cost items in these documents are open, not fixed. `dns` logs cost 52.2s of LLM parsing for a log type with no registered detector — Session 7's `Week_3_plan.md` Priority 1, still unimplemented when Session 9 was written — and `behavioral_http`'s 68.5s was entirely LLM reasoning on 4 false-positive alerts from clean data (the same document records Priority 3's false-positive investigation as never implemented). DNS also spends the LLM call it cannot avoid: 163 lines produced 163 distinct canonical templates at a 0% hit rate, because `canonicalize()` masks neither BIND's `@0x3673a1711f88` client id nor its timestamp. Session 41 left parsing at scale explicitly out of scope, noting the Session 9 500-line live run took ~38 min and that the LLM/template-cache path, not the detectors, is the open scaling question; the same sweep also priced `get_feature_importance` at ~46 ms per flagged window when the population forest is the source (67% of the ssh-corpus 50,000-entity `detect()`, 86 of 128 s), and Session 40 recorded the detector-side defect that made two of its own headline numbers unreadable: the harness wrapped each detector phase in `except Exception` and returned `[]`, so `float('-')` on http `bytes` and `float('1.8 MB')` on package `size` scored 0 recall with an empty `errors` list (its rows A1-A3, later closed as Session 43).
